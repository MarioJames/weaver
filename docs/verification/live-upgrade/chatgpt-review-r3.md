## 一、本轮 R1–R3 的关闭判断

### R1：启动许可与“从未执行”的证明已经分开，关闭

§4.2 第 **199 行**明确：`launchPermittedAt` 与 unit、nonce、logIdentity 同事务提交，**提交后才允许 spawn**。§4.4 第 **220、221 行**又把这一约束落实到包装层透传和 pi 预检停机门。

因此，§11.2 第 **502 行**现在有可成立的判断依据：

| 重启切点 | v3 的处理 | 判断 |
|---|---|---|
| 启动许可尚未提交 | preparing run 可回到 queued | 所有实际 spawn 都必须先提交许可，能够证明尚未获准启动 |
| 许可已提交，实际是否 spawn 不确定 | 不自动回队；待定或确认停止后收尾 | 保守处理提交与执行之间的歧义，避免重复执行 |
| scope 存活 | 按 InvocationID 或受约束的 FD 正向证据接回 | 不再依赖是否已有日志输出 |
| 确认 launcher/scope 已停止，但缺少合法 exit | 按持久意图或 `unknown_outcome` 收尾 | 不再把缺少执行证据转换成自动重跑 |

这里最关键的是：**许可提交后，即使实际上还没来得及 spawn，也不自动回队。** v3 明确接受这部分保守失败，并由 owner 显式决定重试，上一轮“静默执行过却被自动重跑”的反例已经被排除。

第 **494 行**也正确区分了两种证明：inspect → `/proc` 扫描 → 再 inspect 用于确认当前存在性；它不再用于证明历史上从未执行。测试 #31（第 **688 行**）与这条规则一致。

### R2：wait 与结果可读使用同一收尾提交条件，关闭

§11.1 第 **472 行**、§14.2 第 **573 行**及 P1 改动点第 **628 行**均明确：对新文件生命周期的真实 run，只有业务终态与 `finalizedAt` 均已提交，wait/watch 才返回 terminal。

上一轮反例现在变成：

> failed 决定已提交 → wait 继续展示 stopping/recovery pending → 收尾事务提交 → manifest 可读，wait 才可返回 terminal。

第 **474 行**保留了历史记录及 native/mock 的完成条件，避免因缺少新字段而永久等待；原等待截止也被保留。测试 #32（第 **689 行**）直接覆盖了此前的缺口。

此外，第 **476 行**明确保留 `retry --cancel` 的快速替代语义，没有借这次修正扩大为“所有 retry 都必须等待前驱 finalized”。

### R3：native 直接登记与排队 handoff 均已闭环，关闭

§16-P1 第 **621 行**的新取舍成立：

- **有容量的 native**：在接纳事务内完成运行登记，提交后返回 `run_subagent`。事务内发生的是数据库登记，实际子 Agent 仍由 owner 收到指令后创建，因此没有引入“事务未提交便启动外部执行”的窗口。
- **需要排队的 native**：pump 登记 running 后，wait 通过 `reason='handoff'` 交回执行指令，消除了 owner 等待一个尚未由自己启动的子 Agent 的问题。
- **响应丢失或重连**：第 **574 行**规定 handoff 绑定同一 `taskId + attemptId`；owner 已有对应执行句柄时复用原执行，重复读取不会被当成新启动要求。

第 **628 行**已将 handoff 列入 CLI 改动点，测试 #33（第 **690 行**）覆盖 queued → running → handoff 及重复读取。

real `workers spawn` 返回持久接纳、`started:false` 可以是正常状态，也已经在第 **622 行**明确说明，返回语义不再含混。

## 二、前一轮四个核心阻断仍保持关闭

| 核心约束 | v3 中的关闭证据 |
|---|---|
| **finish 批次原子性** | §6.2 第 **274、275 行**：finish records、摘要、最终游标、终态、收尾事件与 `finalizedAt` 同事务；已提交标记的 run 不再应用 finish。§6.3 第 **284、287 行**继续要求整行效果与游标构成完整快照。 |
| **未结束 run 的恢复与结果冻结** | §11.1 第 **468 行**按 run 生命周期恢复，包括 failed 未停止的运行；manifest 收尾前不可见、提交后冻结。§11.3 第 **509、513 行**保留后代清理、最终 EOF，以及已归属但日志损坏时先终止再收尾的要求。 |
| **dispatch/retry 持久意图** | 第 **621、624 行**保留接纳状态、package、关联和稳定 ID 的事务边界；外部 kill/spawn 在提交后推进。native 的事务内登记例外没有破坏外部执行边界。 |
| **单例与 discovery** | 第 **442 行**统一为先锁后开库/迁移，再恢复、pump、ready；第 **450 行**将锁持有期覆盖至 IPC/discovery 清理完成；第 **451、454 行**明确原子发布及锁 FD 不继承、不重建锁文件的不变量。 |

其余关键约束也没有被本轮修改削弱：

- **发布边界**仍是实际 COMMIT 之后；内部 pending 视图继续保留，UI list/get 和定时 flush 通知也已纳入要求。对应 §6.5 第 **303、304、306 行**。
- **取消/失败决定先恢复、终止期限不因重启重置**仍是硬规则。对应 §9.2 第 **391、392 行**、§9.4 第 **409、410 行**。
- **致命错误优先级的矛盾已消除**：第 **337、339 行**把优先级限定于同一未提交决策批次，并保持已提交决定不变；测试 #23（第 **685 行**）同步收敛，不再要求逐行同步提交后还能事后改成另一条流的更高优先级原因。
- **CLI 重连仍有边界**：第 **569 行**保留原截止、不可用宽限、鉴权及协议错误的区分，没有通过无限重试掩盖真实故障。

## 三、可选改进，不影响“通过”结论

以下两处已有明确的具体规则可以消解，属于文字收敛，不构成新的机制阻断。

### 1．将“合法 exit”限定为成功收尾的条件

§11.2 第 **501 行**仍概括为“结束只由合法 exit＋后代清理＋最终 EOF＋收尾事务构成”，而第 **490、502 行**已经明确支持无 exit 的失败收尾。可改为：

> 暂时读到 EOF 不构成运行结束证明。成功收尾要求本 run 的合法退出记录、后代清理、最终 EOF 与收尾事务；确认 launcher/scope 均已停止但缺少合法 exit 时，按第 5 条的持久意图或 `unknown_outcome` 失败收尾。

### 2．将“pump 唯一启动点”明确限定为外部 worker 启动

第 **621 行**前半泛称“不在 dispatch 调用栈直接 `manager.start`”，后半立即规定有容量 native 的登记例外。具体规则已经清楚，可以把前半压实为：

> 需要创建外部进程的 worker，由 pump 在接纳事务提交后启动；有容量的 native 可在接纳事务内完成运行登记，并在提交后返回 owner 执行指令。

**本轮没有需要继续阻塞 P1 实现的修订项。** §17 的故障注入与真实 `weaver.service` 重启演练，继续作为实现验收依据；本次通过确认的是方案已经具备进入 P1 实现的条件。
